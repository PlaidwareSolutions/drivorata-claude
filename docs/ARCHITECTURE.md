# Drivorata — Architecture & Feature Reference

> Living reference for the backend engine + admin app. Hosting and operations live in [DEPLOYMENT.md](./DEPLOYMENT.md); the cutover from Replit is in [MIGRATION-RUNBOOK.md](./MIGRATION-RUNBOOK.md); the storefront integration contract is in [headless-api.md](./headless-api.md).


## Overview
Drivorata is a multi-tenant SaaS platform designed to optimize operations and enhance the online presence of Texas driving schools. It provides customizable marketing websites, an administrative dashboard, student enrollment capabilities, and features to ensure compliance with Texas Department of Licensing and Regulation (TDLR) standards. The platform aims to streamline administrative tasks and improve user experience for both schools and students.

## User Preferences
- Texas TDLR compliance is important; instruction method labels should reference "Texas TDLR Approved"

## System Architecture

### Tech Stack
- **Frontend**: React, TypeScript, Vite, Tailwind CSS, shadcn/ui, Wouter, TanStack Query
- **Backend**: Express.js, TypeScript, Drizzle ORM, PostgreSQL (Railway)
- **Authentication**: Email/password (bcrypt), session-based (express-session, connect-pg-simple), token-based password reset

### Key Design Decisions
- **Multi-tenancy**: Tenant identification prioritizes custom domain resolution with Role-Based Access Control (RBAC) enforced on all API routes. Slug changes include safety checks.
- **Storefront**: The marketing website is a separate app (its own repo, hosted independently) that consumes the headless API (`/api/public/tenant/:slug` + companion endpoints). Drivorata itself does not ship an in-app page builder, public site renderer, or global header/footer editor.
- **Responsive Design**: Utilizes CSS container queries for responsive layouts and includes desktop, tablet, and mobile preview modes.
- **UI/UX**: Professional color scheme (blue/slate) with dark mode support and context-specific CSS palettes.
- **TDLR Compliance**: Package features include instruction methods, age restrictions, and credit hours.
- **Scheduling Engine**: Manages vehicle fleets, instructor availability, session creation with conflict checking, and credit-based student booking. Includes a "Generate Sessions" wizard for recurring sessions.
- **Multi-Role Support**: Users can hold multiple roles with role-aware navigation and conditional field display.

### Core Features
- **Tenant Management**: Creation, customization, and branding for driving schools.
- **Custom Domains**: Support for custom domains with DNS verification.
- **Enrollment System**: Public enrollment forms and admin management with status tracking.
- **Payment System**: Per-tenant integration with Stripe/PayPal/Cash, credit ledger, and automated abandonment cleanup. Each tenant can configure an optional **service fee** with two independent, additive components — both are applied **only** to STRIPE/PAYPAL checkouts (Cash and external/headless flows never carry either): (1) a percentage `tenantPaymentSettings.serviceFeeBps` (integer basis points, default 0, capped at `MAX_SERVICE_FEE_BPS` = 1000 = 10%), and (2) a flat per-transaction admin fee `tenantPaymentSettings.serviceFeeFlatCents` (integer cents, default 0, capped at `MAX_SERVICE_FEE_FLAT_CENTS` = 10000 = $100). Either, both, or neither may be configured. Both are summed by `computeServiceFeeCents(subtotal, bps, provider, flatCents)` in `shared/service-fee.ts` and rolled into the single `payments.serviceFeeCents` surcharge column across all three checkout endpoints (single-package `/checkout/start`, cart `executeCartCheckoutStart`, online-course `/online-course-checkout/start`). The provider is charged the gross amount; the payment row records `amountCents` (gross) plus `serviceFeeCents` (the combined surcharge) and stores `subtotalCents`/`serviceFeeCents`/`serviceFeeBps`/`serviceFeeFlatCents` in `metadataJson` for receipts and refunds. Enrollment `priceSnapshotCents` continues to track the package subtotal so reporting is unchanged. Checkout responses include `subtotalCents`/`serviceFeeCents`/`serviceFeeBps`/`serviceFeeFlatCents`/`totalCents`. The public `/api/public/tenant/:slug/payment-methods` endpoint returns both `serviceFeeBps` and `serviceFeeFlatCents` so storefronts can preview the fee. Tenant admins edit them in `/admin/payment-settings` (Service Fee card — "Service fee (%)" and "Admin fee ($)"); the form converts pct↔bps and dollars↔cents on submit/load. Coverage: `server/__tests__/service-fee.test.ts` (10 unit tests covering pct-only, flat-only, combined, caps, non-card provider, non-positive subtotal, and negative-input clamping).
- **User & Member Management**: Workflows for inviting, editing, disabling members with roles (tenant_admin, office_manager, instructor, student, parent), location scoping, and audit logging.
- **Fleet Management**: CRUD operations for vehicles with status tracking.
- **Scheduling**: Instructor availability, session creation with conflict detection, and student booking with cascading filters.
- **Instructor Dashboard**: Daily session view, student rosters, and attendance marking.
- **Credit System**: Tracks classroom and drive credits with deduction on booking and restoration on cancellation.
- **Platform Administration**: Platform-level view for managing tenants, leads, and support tickets, with impersonation.
- **Lead Management**: Conversion-focused landing page with lead capture, status tracking, notes, and conversion to tenant.
- **Headless API**: Provides API keys for external website integration with public read endpoints and external checkout redirects. Integrator reference for the package + cart endpoints (including `kind`, `tier`, `audience`, `sellableStandalone`, `availableAsUpsell`, `upsellParentPackageIds`, `requiresCohortSelection`, `locationScopeMode`, anticipated 400s, the express-vs-cart flow decision table, the PRIMARY→AUXILIARY tier ordering pattern, and section 3.9 covering the service-fee + admin-fee preview via `/payment-methods` plus the new `subtotalCents`/`serviceFeeCents`/`serviceFeeBps`/`serviceFeeFlatCents`/`totalCents` fields on checkout responses) lives in `docs/headless-api.md`.
- **Support Tickets**: System for tenant users to submit bug reports and feature requests, with a platform-level interface for management.
- **In-App Notifications**: Real-time notifications for system events with unread badges and mark-as-read functionality.
- **Affiliate/Marketing Program**: Supports multiple commission models (Recurring %, Hybrid, Reseller) with affiliate management, referral tracking, and tiered progression.
- **Platform Subscription & Billing**: Manages subscription tiers, tenant billing status, and invoice history. Automated affiliate commission calculation upon invoice payment.
- **Online Courses**: Integration for reselling third-party online courses with admin CRUD and public API endpoints.
- **Enrollment Confirmation Emails**: Automated, customizable emails sent on enrollment and payment receipt, with unsubscribe functionality.
- **Announcement Banner**: Configurable top-of-storefront banner with text, CTA, and styling options.
- **Location Promotions**: Management of promotions with location scoping, package linking, and date validity.
- **Location-Scoped Packages**: Each package has an "Available At" mode — `ALL_LOCATIONS` (default, school-wide) or `SPECIFIC_LOCATIONS` (restricted to checked locations via the `package_locations` junction). Both single-package checkout and the cart's add-item endpoint reject packages not allowed at the buyer's selected location. Headless integrators can pass `?locationId=<id>` to `/api/public/tenant/:slug/packages` to filter; school-wide packages are always included. Existing packages default to `ALL_LOCATIONS` so the change is back-compatible. Per-location **price overrides** are stored on `package_locations.priceOverrideCents` and can be edited from both `/admin/packages` (dialog) and `/admin/packages/:id` (detail page) — both forms hydrate from `GET /api/tenants/:tenantId/packages/:id/locations` and convert dollars↔cents on PATCH. When overrides differ from the base price, the admin packages table and the detail page's header "Price" stat card render a `$min – $max` range (with a hover card listing each location); otherwise they fall back to the single price. Both public package endpoints (`/api/public/tenant/:slug/packages` and `/api/public/tenant/:slug/packages/:pkgId`) include a `locationPrices: Array<{ locationId, priceCents }>` field listing only locations with explicit overrides so storefronts can render the same range on their tiles. Precedence: per-location override → base `price`. Shared rendering helpers live in `client/src/lib/package-pricing.ts`.
- **Student Contact Information**: Student detail page (`/admin/students/:userId`) shows a Contact card with student email/phone/DOB+age and a Parent/Guardian column (hidden for adult students). Editable in place by tenant_admin/office_manager via PATCH on the most recent enrollment; instructors have read-only access.
- **Cart Customer Details Panel**: Read-only Details dialog on Pending Cash (cart-only rows) and Abandoned Carts surfaces the visitor's student/parent contact info plus cart context (package, offering, total, last activity, reminder stats), sourced from the cart's customer snapshot.
- **Contact Messages Inbox**: Storefront contact-form submissions land in `/admin/messages` with All/Unread/Read/Archived filters, search, mark-read toggle, archive/restore, and delete. Submissions trigger a best-effort admin alert email (to active tenant_admin + office_manager, with Reply-To set to sender), a sender confirmation email (suppression-aware, idempotent via `confirmationEmailSentAt`), and an in-app notification with sidebar unread badge. None of these block the public POST.
- **Package & Course Language + Package Image**: Both `packages` and `online_courses` carry a `language` enum (`ENGLISH` / `SPANISH`, default `ENGLISH`, NOT NULL — back-compatible via `npm run db:push`) for marketing/admin display, independent of any locale-aware UI. `packages` also gain a nullable `imageUrl` (online_courses already had it) for an optional hero/listing image stored in object storage. Both fields are editable from the Add Package wizard, `/admin/packages` add/edit dialog, `/admin/packages/:id` detail edit form, and `/admin/online-courses` — the image field is a free-text URL plus an inline ObjectUploader button that PUTs through the existing `/api/uploads/request-url` presigned-URL flow and writes the canonical object path back into the form. Routes spread the fields automatically through POST/PATCH (via the existing `...rest` / `...p` destructuring) and through the public `/api/public/tenant/:slug/packages`, `/packages/:id`, and `/online-courses` endpoints. Coverage: `server/__tests__/simple-packages-and-upsells.test.ts` (default + ENGLISH/SPANISH round-trip + PATCH + public exposure) and `server/__tests__/online-course-location-scope.test.ts` (default + SPANISH POST + PATCH + public list exposure).
- **Package Tier (Primary / Auxiliary)**: Each package carries a `tier` enum (`PRIMARY` / `AUXILIARY`, default `PRIMARY`, NOT NULL — back-compatible via `npm run db:push`). Pure marketing/display knob, independent of pricing/audience/kind. Editable from the Add Package wizard, `/admin/packages` add/edit dialog, and `/admin/packages/:id` (the shared `PackageFormFields` renders a "Storefront tier" radio above Audience). A `Primary`/`Auxiliary` badge with `data-testid="badge-tier-${id}"` renders on every package row in `/admin/packages`. The public `GET /api/public/tenant/:slug/packages` endpoint server-side-sorts the response so PRIMARY packages come first and AUXILIARY come last (stable within each tier by `sortOrder`); the `tier` field is also passed through verbatim so storefronts can render its own grouping if desired. Coverage: `server/__tests__/simple-packages-and-upsells.test.ts` (default + PRIMARY/AUXILIARY round-trip + PATCH + public-list ordering).
- **School Selector Stale-State Fix**: The platform "enter tenant" flag (`platformEnteredTenantId` in localStorage) is now only honored for users whose `/api/platform/membership` response reports `isPlatformMember=true`. Previously a leftover value from a prior platform-admin session (or a different account on the same browser) could silently override a normal tenant member's school selection — clicking their school in the picker did nothing because `tenant-context.tsx`'s auto-select effect kept re-applying the stale `enteredTenantId` on every render. The fix also snaps `currentTenantId` to `tenants[0]` when the saved value points at a tenant the user is no longer a member of, and `platform-context.tsx` actively clears `platformEnteredTenantId` from state+localStorage once the membership query confirms the user is not a platform member.
- **Package Audience Tag**: Each package carries an `audience` enum (`TEENS` / `ADULTS` / `BOTH`, default `BOTH`, NOT NULL — back-compatible via `npm run db:push`) used as a marketing/admin label that is independent of the hard `ageMin`/`ageMax` gating. Editable from the Add Package wizard, the `/admin/packages` add/edit dialog, and the `/admin/packages/:id` edit form. The Packages page renders kind (`Non-cohort`/`Cohort`) and audience (`Teens`/`Adults`/`All Ages`) badges with `data-testid="badge-kind-${id}"` and `data-testid="badge-audience-${id}"` on both tile and table views. SIMPLE packages no longer surface the "Continue setup" affordance, and the Add Package wizard's submit label flips to "Save Package" for SIMPLE existing packages (still "Save Cohorts" for COHORT_BASED, "Create Package" for new). Round-trip coverage in `server/__tests__/simple-packages-and-upsells.test.ts`.
- **Simple Packages & Upsell Dependencies**: Each package now carries a `kind` (`COHORT_BASED` default, or `SIMPLE` for products like Road Test or School Car that have no class schedule) plus two channel flags — `sellableStandalone` (default true; appears in the storefront packages list and is allowed in single-package checkout) and `availableAsUpsell` (default false; appears in the cart upsell list). A `package_upsell_dependencies` junction (`upsellPackageId` → `parentPackageId[]`, scoped by `tenantId`) lets each upsell-only add-on declare which parent packages must be in the cart before it can be added (e.g. School Car only shows when Road Test is in the cart). With no rows configured, an upsell falls back to legacy generic add-on behavior (any non-empty cart). Cart guards: `addCartItem` skips the cohort/offering check for SIMPLE packages and rejects packages with `sellableStandalone=false` unless one of their declared parents is already in the cart; `listCartUpsells` filters add-ons by those dependencies; `listAddOnPackages` ORs `isAddOn`/`availableAsUpsell` and accepts a `parentPackageId` filter. Single-package checkout (`/api/public/tenant/:slug/checkout/start`) only blocks the cohort-pick flow when `kind==="COHORT_BASED"` and refuses any package whose `sellableStandalone===false`. The public packages list (`/api/public/tenant/:slug/packages`) hides packages with `sellableStandalone===false`. Admin package routes (GET/POST/PATCH `/api/tenants/:tenantId/packages`) accept and return `upsellParentPackageIds` plus a derived `requiresCohortSelection` flag. The Add Package wizard switches to a 2-step Package → Review flow when `kind==="SIMPLE"` (skipping Cohorts/Sessions, sending an empty cohorts array even if the user toggled mid-flow); the Package step exposes a Sales-channels block with the two flags + a parent-package picker, and warns when both flags are off. The package admin pages (`/admin/packages` dialog and `/admin/packages/:id`) hydrate and edit the same fields. A one-time backfill `scripts/backfill-package-kind.ts` (supports `DRY_RUN=1`) sets `kind=COHORT_BASED` when the package has any classroom/drive hours (else SIMPLE), and maps legacy `isAddOn` to `sellableStandalone=!isAddOn` + `availableAsUpsell=isAddOn`. Coverage: `server/__tests__/simple-packages-and-upsells.test.ts` (workflow `test:simple-packages-and-upsells`).
- **Re-link Cohort to Different Package**: Admins can re-parent any `schedule_offerings` row to another package in the same tenant from three surfaces: an `ArrowRightLeft` icon button on each cohort tile (`button-change-package-${id}`) and table row (`button-change-package-row-${id}`), an outline "Change package" button in the offering-detail header (`button-change-package`), and a bulk "Move to package…" toolbar action that appears in the table view once one or more cohorts are checked (multi-select via the row checkboxes — `checkbox-select-offering-${id}` and the header select-all). The shared `ChangeOfferingPackageDialog` + `BulkMovePackageDialog` in `client/src/components/admin/change-offering-package-dialog.tsx` use the same PATCH endpoint and a shared native shadcn `Select` target-package picker (Radix Select — avoids the cmdk-inside-Radix-Dialog click-swallowing bug) that hides the current package and sorts PRIMARY tier first, AUXILIARY last; each option shows an audience badge (Teens/Adults/All ages), an `Aux` tier badge, and the package's age range. The picker is restricted to `kind === "COHORT_BASED"` packages only (SIMPLE/one-off packages can't hold a cohort), and the Save button is decoupled from the move-impact query's loading state — it enables as soon as a valid target is picked (the server still enforces all guards via the 409 audience-mismatch + 400 cross-tenant checks). Before submitting, the single dialog calls `GET /api/tenants/:tenantId/schedule-offerings/:oid/move-impact` to preview the cohort's `bookedSessionCount`, `confirmedEnrollmentCount` (statuses `pending`/`confirmed`/`active`/`in_progress`/`completed`; cancelled and refunded are excluded), and `enrolleeAges`; the bulk dialog fetches the same impact for every selected cohort in parallel and renders a per-cohort row with `Nb · Ne` and a `will move` / `already on target` / `out of range` badge. When the cohort has any bookings or active enrollments, a yellow snapshot notice explains that existing bookings keep their original pricing and enrollment `priceSnapshotCents` is frozen — new bookings use the target package's terms. If any enrollee's current age falls outside the target package's `ageMin`/`ageMax`, an inline red audience-mismatch warning is rendered client-side, the Save button is disabled (single dialog) or the offending cohorts are skipped (bulk dialog), and the server enforces the same gate. Server-side hardening on `PATCH /api/tenants/:tenantId/schedule-offerings/:oid`: when the request changes `packageId` it (a) verifies the target package belongs to the same tenant (400 otherwise), (b) re-runs the age check via the move-impact helper and returns `409 { code: "OFFERING_PACKAGE_AUDIENCE_MISMATCH", conflictingEnrollmentIds: number[] }` if any active enrollee is out of range, and (c) on success writes a single `OFFERING_PACKAGE_CHANGED` audit row with `details: { offeringId, fromPackageId, toPackageId }` (PATCH with the same `packageId` is a tidy no-op that skips the audit). Coverage: `server/__tests__/offering-change-package.test.ts` (5 tests — happy path + audit, same-package no-op, audience-mismatch 409, cross-tenant 400, move-impact counts), workflow `test:offering-change-package`.
- **Package → Schedule Offering (1:N)**: Each `schedule_offerings` row belongs to exactly one package via a NOT NULL `package_id` foreign key (`onDelete: "restrict"`). The legacy `offering_packages` junction has been dropped — an offering cannot be shared across packages. The one-time migration `scripts/backfill-offering-package-id.ts` (idempotent, supports `DRY_RUN=1`) adds the nullable column, backfills from the junction (deterministic lowest-package_id wins on multi-link anomalies, with a per-row report), aborts if any offering is left without a package, then sets NOT NULL + FK + index and drops the junction table. POST `/schedule-offerings` requires `packageId`, and DELETE `/schedule-offerings/:id` strictly returns 409 with the conflicting session ids if any session has bookings (no cascade); otherwise it deletes the offering and its sessions transactionally. The admin Offerings page surfaces the 409 message and booked-session count in the toast. Recurrence helpers (`buildOccurrences`, `checkAvailabilityCoverage`) live in `shared/recurrence.ts` and are reused by the routes and the Add Package wizard. The 4-step **Add Package wizard** (`client/src/components/admin/wizards/add-package-wizard.tsx`) — Package → Cohorts → Sessions → Review — replaces the old single-form Add Package dialog; it is launched from `/admin/packages` and the dashboard "New Package" Quick Action, supports per-cohort optional recurrence (with a 200-session cap surfaced on the Sessions step), and persists progress with a Save & Exit button — for new packages, when the package form is valid the wizard POSTs the package (plus any valid cohorts/sessions) so the admin can resume from the package row later; otherwise it falls back to `localStorage` under `add-package-draft:${tenantId}`. A "Continue setup" action appears on any package that has no cohorts or any cohort with zero sessions, and reopening hydrates existing cohorts (locked when they already have sessions; recurrence is configurable when sessions are still empty). POST `/api/tenants/:tenantId/packages` accepts an optional `cohorts[]` array of `{ offering, recurrence? }` and creates the package + its cohorts + (when recurrence is provided) its sessions in one transaction via `storage.createPackageWithCohorts`.
- **Dashboard Quick Actions & Wizards**: The admin dashboard exposes a Quick Actions panel that is shown only to tenant_admin/office_manager/platform_admin (returns null for instructor/student view-roles — no read-only badge). Shortcuts either deep-link existing pages with `?create=1` (Add Vehicle, Add Location, Add Package, Add Promotion, Schedule Session — auto-opens the create-session dialog on `/admin/schedule-sessions`) / `?invite=1` (Invite Member) or open guided multi-step wizards. Three wizards live in `client/src/components/admin/wizards/`: Manual Enrollment (package + location + offering picker → student/parent contact → payment method PENDING/CASH_PAID/EXTERNAL → POSTs `/api/tenants/:tenantId/admin-enroll`, creating an enrollment plus a COMPLETED CASH `payments` row when paid and confirming via `confirmEnrollmentManually`); Private Lesson (drive offering → instructor + vehicle + location + start time → student picker → reuses `POST /api/tenants/:tenantId/sessions` and `POST /api/tenants/:tenantId/bookings`); Broadcast Message (audience selector ALL_MEMBERS/ALL_ACTIVE_STUDENTS/ROLE_*, optional location filter for member-based audiences → channel toggles email/in-app → subject + body → preview via `POST /broadcasts/preview` showing recipientCount/emailCount/inAppCount → send via `POST /broadcasts`). Audience resolution dedupes by userId-or-email, honors `tenantMembers.locationScope`, and ALL_ACTIVE_STUDENTS sources from `enrollments` with status confirmed/active/in_progress. Send writes a `BROADCAST_SENT` audit event and uses `sendEmail()` (suppression-aware) for email and `storage.createNotification` (`type: "ticket_update"`, `link: "/notifications"`) for in-app, returning per-channel tallies.

## External Dependencies
- **PostgreSQL**: Primary database.
- **bcryptjs**: For password hashing.
- **cors**: For cross-origin headless API access.
- **Stripe**: For payment processing and webhooks.
- **PayPal**: For payment processing.
- **Resend**: For transactional email delivery, including bounce and complaint handling via webhooks. Requires API key and verified sender domains.
## Hosting (post-migration)
- **Railway**: one web service (Dockerfile, Node 22) serving the API and the admin SPA; Railway Postgres; pre-deploy `node dist/migrate.cjs` applies Drizzle migrations.
- **Cloudflare**: DNS/proxy for `drivorata.com`; **R2** for uploads (`server/object-storage/`); **Cloudflare for SaaS** custom hostnames for each school's staff portal (`portal.<school-domain>`) with the `infra/cloudflare/portal-proxy` Worker as fallback origin (`server/cloudflare/`).
- **Background jobs** (`server/jobs/scheduler.ts`): expiry cleanup and reminder emails run in-process under a Postgres advisory lock, so extra replicas never double-send.
